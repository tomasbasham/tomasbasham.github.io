Monitoring Pods with tcpdump and tshark

Blog Logo

Tomas Basham

on 18 Mar 2018
About 4 min read

I remember when I first started to learn about the exciting world of operations, when it was far easier to execute commands on a remote machine and capture logging information and packet traces to the remote hosts storage medium to later be analysed by more sophisticated tools.

However in today’s world of containers, kubernetes and distributed systems (or distributed complexity 😛) there are often limited resources on offer to facilitate the same level of diagnostic. By and large logs are intercepted from stdout and routed to a dedicated application infrastructure and monitoring platform such as Google Stackdriver or Amazon CloudWatch.

As for more detailed IP packet traces these would have been written to a pcap file and viewed later in an application like Wireshark. To the best of my knowledge there are no equivalent cloud services to store this data. Luckily our options are not exhausted; in such situations I reach for kubectl exec, tcpdump and tshark.

It is important to note that in order for this to work the kubernetes pod is required to have tcpdump already installed. I would not typically advocate installing software that is not necessary for the normal operation of a production application, but in this scenario there is little choice. Furthermore after capturing packets I would typically delete the pod under test and have kubernetes spin up a new one, effectively removing tcpdump from the container.

So first we need to select a pod whose packets we wish to capture. A good example would be an API application receiving a good amount of traffic. Grab the name of the pod using kubectl get pods.

kubectl -n myapp get pods -l tier=api
NAME                   READY     STATUS    RESTARTS   AGE
api-4146221093-7pv1p   2/2       Running   0          200d

With a pod chosen we need to install tcpdump (if not already installed on the container). Depending on the package manager available on the container this could look slightly different. Using apt the command would look like this:

kubectl -n myapp exec api-4146221093-7pv1p -c api apt-get update -qq
kubectl -n myapp exec api-4146221093-7pv1p -c api apt-get install -y tcpdump

Now that tcpdump has been installed on the pod IP packets can be captured and routed back to the local host using a combination of kubectl exec, tcpdump and tshark.

kubectl -n myapp exec api-4146221093-7pv1p -c api -- tcpdump -s 0 -U -n -w - | sudo tshark --color -i -
Running as user "root" and group "root". This could be dangerous.
tcpdump: listening on eth0, link-type EN10MB (Ethernet), capture size 262144 bytes

Here instead of writing the captured packets to a file (typical use case) -w - redirects the tcpdump output through stdout which is further redirected through the remote session created by kubectl exec. Then on the local host this data is piped into tshark, capturing on stdin. Of course tools like Wireshark can still be used instead of tshark if a GUI is preferred; or alternatively the captured output could be redirected to a file using tee as before.

Regardless of the use case, or how one needs to visualise the data, this technique is very useful and something I hope to continue using whilst developing microservice architectures using kubernetes.
