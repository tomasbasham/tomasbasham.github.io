AI-Generated Code Doesn't Change What Good Delivery Looks Like

Blog Logo

Tomas Basham

on 15 May 2026
About 4 min read

There’s an idea doing the rounds that because AI can generate code faster than any team, the bottleneck in software delivery has moved: code is now cheap, even disposable, and the real constraint is understanding, evaluating and governing it. I think that’s largely correct, but it carries an assumption worth pulling apart: that the infrastructure underneath the software can absorb whatever gets thrown at it. It can’t, not without deliberate design, and the people who’ll feel that first aren’t developers — it’s whoever is responsible for keeping things running while the velocity of change accelerates around them.

Code as something you throw away

Chad Fowler’s Phoenix Architecture series makes the case that the durable part of a system isn’t its implementation, it’s the evaluations that define correctness: the interfaces, the behavioural contracts, the tests that would still hold if the whole thing were rewritten in a different language. Code, on this view, is closer to cache than to capital — a materialised view of intent that’s fine to discard and regenerate, provided the intent itself is written down somewhere that survives the rewrite.

None of this is actually new. Experienced engineers have always known that the most expensive code is the code you keep, and rewrites have always been underrated relative to their reputation. What’s new is the pace this cycle can now turn at, and the volume it can produce while turning.

Where the strain actually lands

When the rate of change goes up, something has to absorb it, and that something is the deployment target — the platform, the infrastructure that accepts artefacts and runs them. On a fleet of hand-provisioned servers, each with its own accumulated quirks and institutional knowledge, every deployment is a small negotiation with the specific machine it’s landing on. That friction has historically been self-limiting: snowflakes accumulate, runbooks grow, and the rate of change slows to match what the platform can actually absorb.

Generative AI doesn’t reduce that friction. It bypasses it at the application layer while leaving it completely intact underneath, which widens the gap between how fast software can be produced and how safely it can be deployed. Platform teams end up facing more deployments, more varied workloads, less consistent artefact quality, and more pressure to move quickly, without any corresponding change to the infrastructure complexity they’re managing. Historically, what gives first under that pressure is operational discipline.

The infrastructure for this already exists

The useful part is that the industry has spent over a decade building the answer to this, for entirely unrelated reasons: scale, reliability, cost, and the general desire to stop treating infrastructure like a collection of pets. The underlying idea was to make the unit of deployment portable and self-describing, so the artefact stops depending on the specifics of the machine it runs on.

Containers are that idea, implemented. They changed operations less because process isolation was technically novel — it wasn’t — and more because they changed the contract between development and operations: a container image is a promise that running it will produce the described behaviour, on any machine that honours the contract. That’s precisely the property regenerative software needs. If implementations are going to be thrown away and regenerated at pace, the deployment target needs to be indifferent to exactly what it’s running — whether a given version was written by a person, generated by a model, or some mixture of both.

Kubernetes is the same idea at orchestration scale. Strip away the operational complexity around it and what’s left is a system for expressing desired state and continuously reconciling reality against it: three replicas, this much memory and CPU, reachable at this address, replaced automatically if unhealthy. That reconciliation loop doesn’t care how the new version was produced — rolling out a hand-crafted release and rolling out one generated overnight are the same operation to the scheduler. Teams running mature Kubernetes platforms are, as a direct consequence, structurally ready for AI-accelerated delivery in a way that teams without one aren’t: the primitives built to absorb human-authored churn are the same primitives that absorb AI-authored churn.

The seam needs more discipline, not less

The corollary Fowler’s argument doesn’t quite spell out is that the seam between disposable code and durable platform needs more care than either side individually — the health checks, resource declarations, shutdown behaviour, privilege model and image construction that make up the container contract. In human-authored software, violations of that contract accumulate slowly enough that a team notices during an incident and fixes it; the feedback loop is long but it works. Under AI-accelerated delivery, the volume crossing that seam goes up enough that violations stop accumulating slowly and start arriving in batches.

Which means the right response to AI-driven velocity isn’t to relax platform discipline, it’s to enforce it earlier and more systematically — not as a gate that slows delivery, but as the contract that makes the platform’s indifference to what it’s running sustainable in the first place.

The point

The teams that come through this well won’t be the ones generating the most code. They’ll be the ones who already invested in a deployment target capable of accepting, validating and running whatever gets generated, quickly and repeatedly. That investment predates AI by a decade and was made for entirely different reasons — scale, reliability, cost. AI hasn’t created the need for it. It’s just made ignoring it considerably more expensive.
